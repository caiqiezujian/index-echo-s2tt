# Index-Echo 英中流式同声传译系统：完整技术与部署方案

**版本：1.0｜资料核查：2026-10-08｜部署顺序：Linux NVIDIA A800/A100 → 华为昇腾 910B**

本文是待实施的设计基线，不是已经运行成功的系统说明。已完成三类调查：开源框架与接口、Echo 模型与增量解码、评测与跨硬件部署。公开源码已通过网页核查；本次没有在用户服务器运行模型，没有真实延迟、显存或并发实测。文中的初始参数和性能目标均为研发起点。

用户称谓“昇腾 D910B”在本文统一记作“Ascend 910B”；实际芯片、板卡、服务器 SKU、HBM、CPU 架构和驱动以现场盘点为准，不根据这个简称推定具体硬件。

引用编号对应 `04_调查证据与学习资料.md`。设计要求、建议阈值和数学推导与外部已确认事实分开表述。

## 0. 执行摘要与最终选型

### 0.1 主线

**simulstream 接入/评测底座 + 独立 SessionCore + IndexEchoBackend + 增长音频前缀重译 + 稳定提交策略。**

首版使用 2B，在 A800 或 A100 上建立真实模型、完整英中、部分音频和长流四个基线。9B 是质量对照，不能仅更换目录而不核对组件。第一版不修改权重，不预先依赖跨音频更新的 KV cache。模型常驻，一次生成内部按模型原有支持使用缓存。

硬件无关部分从第一天保持纯 CPU/Python 语义；CUDA 和 Ascend 的设备操作分别封装。NVIDIA 跑通后，910B 首先通过 TorchNPU 参考路径验证正确性，再考虑专用算子、图模式或 vLLM-Ascend。不要同时研究流式策略、换推理引擎、换硬件和量化，否则无法定位误差。

### 0.2 备用路线

保留明确命名的级联对照：**流式英语 ASR → Index-Translate 文本翻译 → 同一套提交/展示/评测协议**。该对照用于判断“问题出在音频模型、翻译模型还是流式策略”。它不是 Echo 端到端模型；禁止在主模型失败时悄悄切换后仍报告 Echo 效果。

### 0.3 传输选择

浏览器演示与第一版服务复用 WebSocket；原生客户端/服务间调用需要时，增加 gRPC 双向流网关。两个入口调用同一 SessionCore。gRPC 支持双向流，但协议并不提供 READ/WRITE 决策、语义稳定性、源音频缓存正确性。[S01–S03, S15–S17]

### 0.4 首版不做

不做 TTS/声音克隆，不做跨机器模型并行，不先做 Kubernetes/Kafka，不承诺任意语言，不启用未经验证的跨更新缓存，不先把模型导出为 ONNX/MindIR，不把 vLLM/MindIE/量化当作必经之路。

## 1. 三轮调查与决策依据

### 第一轮：开源框架能复用到哪一层

| 对象 | 核查结果 | 决策 |
|---|---|---|
| simulstream | 提供 WebSocket、文件回放/推理、浏览器演示、自定义 SpeechProcessor 和评价接口。 | 首选底座，不从裸 gRPC 重新写全部研究工具。 |
| SpeechProcessor / IncrementalOutput | 接口可适配自定义模型；输出描述新增/删除 token 或文本，不包含本项目完整的稳定提交合同。 | 外接适配器；自建提交台账和事件协议。 |
| Whisper-Streaming | LocalAgreement 对包含新增音频的连续假设确认公共前缀。 | 采用思想作首个可解释策略，不照搬 Whisper 时间戳/语言假设。 |
| AlignAtt4LLM | 提供 decoder-only 翻译模型适配说明。 | 后续文本翻译策略或注意力研究参考，不是现成 Echo 插件。 |
| Qwen3-ASR-causal | 发布因果化音频塔及流式运行时，并披露速度/质量取舍。 | 仅作原生流式研究参考，不把该音频塔直接替换 Echo。 |

结论：存在“可插入自定义处理器”的开源系统，但没有证据表明本方案所需的 Echo 英中适配、稳定提交与双硬件部署已经全部完成。simulstream 是研究/演示底座，不自动等于生产级会话管理和安全服务。[S01–S03, S18, S21–S24]

### 第二轮：Echo 实际代码与能力边界

| 核查项 | 观察 | 工程约束 |
|---|---|---|
| 组成 | 音频编码器、连接模块、Index-Translate 派生解码器。 | 不能只加载文本模型即称 Echo。 |
| 官方“stream”函数 | 先转换完整文件、对完整文件 VAD，再逐窗翻译。 | 在线端不调用这条完整文件路径。 |
| 2B/9B 指令 | 2B 所查指令表含 en/ja/es；9B 含 zh 等更多目标语。 | 两者分别验证中文指令，不能共用未经检查的补丁。 |
| 命令行 | 所查两包目标语言选项仍为 en/ja/es。 | 命令行限制不等于权重不具备能力；指令存在也不等于已验证质量。 |
| 连接模块 | 9B 代码增加投影型连接模块，并根据权重键选择。 | 9B 不只是“把 2B 目录换掉”；按权重/配置构造，严格加载。 |
| 输出 | 时间戳、源转写、目标译文；旧字段使用 zh/en。 | 统一内部 source_text/target_text，保留 raw output。 |
| 2B 解码器 | 配置包含线性注意力与完整注意力混合层。 | 缓存、门控与设备适配须兼顾不同状态，不能按普通全注意力 LLM 处理。 |
| 官方环境 | 模型卡给出 PyTorch 2.11.0、Transformers 5.6.0。 | 作为复现候选起点，需检查包文件、驱动和依赖锁定。 |

官方英中评测是实验依据，不是公开短前缀英中已经通过验收的证明。上述事实来自模型卡和代码，不是本次 GPU 实测。[S04–S07]

### 第三轮：算法、评测与硬件迁移

LocalAgreement、重译、注意力门控、历史选择分别解决不同问题；不能用一个“stream=True”代替全部。StreamAtt 特别说明长流的音频历史选择值得单独处理。因果化编码器也有精度代价，不能仅用减少计算量判断成功。[S18–S25]

TorchNPU 官方矩阵列出 PyTorch 2.11.0 与 TorchNPU 2.11.0.post2、CANN 9.1.X 的组合。vLLM-Ascend 有 Qwen3.5-Dense 2B/4B/9B 教程，但所查支持模型页未出现 Index-Echo；这只表明相关模型家族有可借鉴路径，不证明 Echo 整包可直接服务。[S08–S12]

最终采用：**NVIDIA 正确性基线 → 单卡在线策略 → 长流/性能验收 → 910B 逐组件迁移 → 双硬件回归 → 有证据的进一步优化。**

## 2. 成功定义与需求边界

### 2.1 用户目标

输入为不断到达的英语音频，输出为持续更新的中文字幕。输出分可修改草稿与已提交文本。希望在长句尚未结束时已经提交正确、具有实际意义的中文，而不是只在讲话结束后生成完整翻译。

### 2.2 三个层级必须分别验收

**L1 在线字幕**：持续收音、实时草稿、边界后稳定输出。可能仍等句末，不宣传为已实现句中同传。

**L2 增量同传**：严格不可见未来输入；长句结束前有正确的语义单元被稳定提交；有真实时钟和质量证据。

**L3 原生增量推理**：新增音频复用已验证的编码/解码状态；与正确参考路径有一致性比较，计算成本不因长期累计而失控。

L1 成功不意味着 L2，L2 成功也不意味着 L3。阶段报告同时标注功能等级和质量/延迟是否达标。

### 2.3 初期明确范围

固定英语→简体中文；用户明确指定语言，首版不自动语言识别。单路主要说话人音频；多说话人交叠可以作为困难样例，不宣称首版解决分离。连续会话、静音、取消、正常结束、断连重连、术语表和异常输入必须有明确行为。

现场 GPU/NPU 数量、具体显存、网络 RTT、讲话场景和并发目标未给出。这些不阻塞设计；先按单卡单会话完成，现场盘点后补全容量配置。

## 3. 架构与模块职责

```text
浏览器麦克风 / 原生客户端 / 因果文件回放
                 ↓
        WebSocket 或 gRPC 网关
                 ↓
       AudioNormalizer + AudioLedger
                 ↓
  SessionCore（VAD、触发、任务版本、背压）
                 ↓
         受控 ModelWorker
                 ↓
IndexEchoBackend ── DeviceProvider(CUDA / Ascend)
                 ↓
 HypothesisParser → HypothesisAligner → CommitPolicy
                 ↓
     HistoryManager + EventLedger
                 ↓
     草稿 / 稳定追加 / 明确更正 / 告警
                 ↓
   字幕界面、离线回放、监控与质量评分
```

图为拟实施结构，不是上游已存在的完整服务。

### 3.1 AudioNormalizer

维护连续重采样状态，转换为 16 kHz 单声道 float32。输入可为协商好的 PCM16LE。处理通道、幅值、样本数、时钟映射与丢包标记。每个小包单独重采样而不保留滤波状态会引入边界问题，应通过连续/分块等价测试防止。

### 3.2 AudioLedger

唯一持有源音频索引和可见边界的模块。使用绝对采样点，而不是用浮点秒累加。记录接收终点、实际交付模型终点、可删除终点、缺口区间、epoch 及原始帧序号。提供不可变快照；模型后端不接触整个原始录音路径。

### 3.3 SessionCore

维护每个会话的状态机、在线 VAD、推理触发、待处理快照、结果有效性、语义提交状态和结束处理。不得直接调用 CUDA/NPU 专属 API。

### 3.4 ModelWorker / IndexEchoBackend

模型在 worker 启动时加载一次。首版一个 worker 同时只进行一次真实生成。权重共享，会话历史和状态隔离。后端按完整且冻结的音频前缀生成假设，不负责 UI、网络或稳定提交。

### 3.5 Parser / Aligner / Policy

Parser 将模型三行结构转换为规范对象。Aligner 将不同更新的源区间和假设建立可核查对应。Policy 在约束下决定继续等待、更新草稿、提交或触发冲突，三者不能混成一个“字符串去重函数”。

### 3.6 HistoryManager

管理已确认双语历史、术语表版本和音频裁剪凭据。一个 epoch 内冻结输入历史；不要一边重复输入同段完整音频，一边把当前段新提交文字又追加为前文，造成重复条件和自我强化。

### 3.7 EventLedger / Evaluator

事件顺序是产品和评测的共同真值。先保存在线实际输出，再计算最终质量与延迟。独立评分环境可以访问完整参考，但不能把参考或未来 VAD 传回推理进程。

## 4. 数据合同与状态机

### 4.1 三个光标与版本

- received_end：已收到的原始音频终点。
- used_end：本次生成实际看到的音频终点。
- evict_before：允许从主缓冲删除的音频边界。

不变量：`evict_before <= used_end <= received_end`，并保留必要重叠和未覆盖区间。已提交中文长度不能推导 evict_before。

每个任务携带 session_id、epoch_id、generation_id、snapshot_start/end、history_hash、prompt_hash、model_revision、policy_version。新任务覆盖排队中的旧任务，但不抹掉旧任务尚未处理的音频。

### 4.2 会话状态

`CREATED → READY → RECEIVING ↔ DECODING → DRAINING → CLOSED`；另有 `DEGRADED`、`ERROR`、`CANCELLED`。

DECODING 时继续收音，不阻塞网络。DRAINING 停止接受新的正常音频并处理已确认接收的尾段；End 消息必须提供最后帧序号用于检查。Cancel 与 End 不同，取消不强制生成“最终译文”。

### 4.3 后端能力对象

至少声明：支持的模型/方向及其验证状态、要求的输入采样率、返回格式、时间戳类型、可用精度、最大已验证输入、是否支持一次生成内部缓存、是否支持跨更新状态复用、是否支持安全目标前缀约束。

这些是能力合同，不是从配置名称猜测。实验性英中方向要显式标记 `experimental`；只有真实验收后升级。

### 4.4 假设对象

保存 raw_text、解析状态、source_text、target_text、cues、模型时间戳、输入快照边界、生成结束原因、token 数、运行耗时、设备、dtype。时间戳缺失则标 unavailable，不自动编造。

结构错误分级：完全不可解析；源转写存在而译文缺失；仅尾 cue 截断；时间戳不合法；时间戳超出已用音频；源/目标字段异常。完整且合格的前部 cue 与不完整尾部可分开处理，但不能把残缺尾部强行提交。

### 4.5 输出事件

核心事件为 DraftSnapshot、CommitAppend、Correction、Boundary、Warning、StreamEnd、Error。每个事件包含 session_id、event_seq、output_version、used_audio_end_sample、server_emit_time 和策略原因。

草稿优先发送完整快照，避免中英文混合时 UTF-8 字节、Unicode 字符和前端 UTF-16 长度混淆。CommitAppend 同时带提交增量及提交后的草稿快照，或通过原子 output_version 更新，避免前端短暂重复显示同一句。

Correction 引用被更正的 commit_id 和替换内容；不允许静默重写已提交历史。更正发生不意味着系统可靠性自动失败，但必须计入错误率，不能从最终统计删掉。

## 5. simulstream 与服务协议接入

### 5.1 上游接口核对

实际 SpeechProcessor 定义在 speech_processors 包入口；BaseSpeechProcessor 为部分实现。源码、README 与在线文档可能不同步。编码代理必须核对锁定 commit 的实际构造器、加载、处理音频、语言配置、结束和清理接口，不凭本文拼接不存在的导入路径。[S02]

IncrementalOutput 的新增/删除表示映射为本项目 `committed + draft` 的展示差分。本项目独立保存提交边界。上游评测若只收到稳定输出，必须标明 `stable_only`；收到含草稿修订的输出则标明 `revision_stream`，两种指标不能混用。[S03]

### 5.2 服务层取舍

首版保留 simulstream 原生回放与演示入口。复杂会话/安全控制可以通过薄网关加入，但不要为一个单卡实验先建设完整微服务平台。GPU 阻塞推理应在独立 worker 或明确执行器中运行；不能假设 async 函数天然让同步模型调用不阻塞。

### 5.3 gRPC 拟定合同

```proto
// 仅为协议设计示意，需本地实现和生成代码。
service SimultaneousTranslation {
  rpc Translate(stream ClientMessage) returns (stream ServerEvent);
}
```

ClientMessage 分 Start、Audio、End、Cancel、Ack。Start 包含协议版本、源/目标语种、输入格式、采样率、会话恢复令牌；模型 ID 从服务器白名单选，不能传任意本地路径。Audio 带 frame_seq、first_sample、样本数和 bytes。ServerEvent 使用统一事件语义。

重连基于最后确认的 event_seq 与音频序号；重复包可幂等识别，缺口明确记录。不得声称 gRPC 自动提供跨断连“恰好一次”。如果服务端缺少所需上下文，返回不可恢复状态并新建 epoch，而非假装连续。

### 5.4 浏览器边界

官方 grpc-web 当前不支持客户端流和双向流，所以浏览器初版使用 WebSocket。原生 Python/C++ 客户端可用 gRPC。远程麦克风页面的安全上下文、用户授权和代理超时须作为部署测试项，不能只在服务器上传 WAV 验证。[S15–S16]

## 6. 音频前端与因果性

内部统一 16 kHz；网络 20–40 ms 小包是初始设计，模型更新周期单独配置。VAD 按其实现要求聚合合法帧长，不能把网络包长直接当 VAD 帧长。

在线 VAD 仅消费已经到达的输入；前后填充只使用当前已知边界。VAD 用于触发、节省静音计算和边界候选，不代表完整语义句末。长时间无静音仍必须有控制策略。

不为每个窗口启动 ffmpeg、写临时 WAV 再读回来。ffmpeg 可用于离线参考和入口解码，不应成为每次低延迟更新的磁盘往返。

处理：不同采样率、双声道、幅值溢出、截断样本、空包、重复包、缺帧、乱序、网络时间抖动。首版严格顺序模式可以拒绝乱序；不偷偷丢弃或填零。真实静音与网络缺失使用不同状态。

音频归一化、特征提取和后续模型只基于快照；不能先计算完整录音的统计量或特征后再切片，用“预处理”引入未来信息。持续重采样/滤波若存在固有等待，把这部分计入延迟。

## 7. Echo 模型适配细则

### 7.1 先建立原版健康参考

在用户服务器保存不可变官方脚本和权重 manifest。用官方已开放方向做健康检查；随后测试完整英中。避免将下载、dtype、组件或解析错误误判为英中能力问题。

### 7.2 内存音频路径

添加以音频数组为输入的编码路径，保留官方特征配置、有效帧处理和音频嵌入注入顺序。同一个已规范化 WAV 的文件路径与内存路径要比较波形、特征形状、有效长度、编码器输出、连接输出、提示 token 和解码结果。先做到功能等价再去掉文件路径。

### 7.3 2B 与 9B 分离加载

根据实际权重键和配置识别连接模块，严格加载；不允许用 `strict=False` 掩盖大量缺失/多余键。检查解码器实际类、隐藏维度、特殊 token、占位符数量、音频塔输出维度与位置编码。

9B 源码存在投影式连接模块，这是独立于提示语的差异。分别写两份真实模型集成测试，不能只用 2B 的 mock 覆盖 9B。[S05–S07]

### 7.4 英中指令与字段

2B 增加中文目标指令时，首先沿用公开三行训练模板，不直接改为“只输出新增中文”。9B 测试内置中文指令，并修正路由/命令行限制。所有结果以源/目标命名，旧 zh/en 字段只在兼容层出现。

是否真正英语→中文须同时看源转写与目标译文；模型输出中文不等于正确完成翻译。英文片段的否定、数字、专名和尾部信息必须人工抽检。

### 7.5 术语与提示稳定性

术语表在会话开始或 epoch 边界固定版本；长度受限。更改术语/提示后重置一致性历史。保留原特殊 token，不把用户术语字符串允许为任意模板或路径。语音内容即使像指令，也应作为待翻译数据处理。

## 8. 解码路线与提交算法

### 8.1 四组基线

B0：完整音频离线参考，只在离线进程读完整输入。

B1：在线边界分段，对当前已知语段重译；可以持续显示草稿，但稳定输出可能较晚。这是工程正确性对照。

B2：同一 epoch 固定起点、增加音频终点，重复推理并使用 LocalAgreement 候选提交。

B3：在 B2 之上单独测试源边界检查、不同尾部保留、有限前缀约束或注意力门控。不要一次加入全部策略。

### 8.2 生成参数

默认不采样，先保留官方停止 token 和提示。EOS 仅表示本轮假设结束，不表示麦克风会话结束。达到 token 上限时记录 `length`，不能把不完整 cue 当成最终译文。

原版长窗口的 token 预算不能机械用于每秒更新；先测时间戳/源转写/目标译文分别耗费多少 token，再设置随有效输入长度增长的上限。过小上限截断译文时不能报告为“模型不会英中”。

beam search 不等于同传策略；更大的 beam 可能增加每轮计算，也可能改变重译稳定性，作为独立实验。训练前不要随意引入未学习的 WAIT 特殊 token。

### 8.3 LocalAgreement 的正式约束

设同一 epoch 第 k 次自由假设为 H_k。只有源音频确有新增、history/prompt 版本可比较时，才加入一致性序列。候选前缀为最近 n 次假设的 LCP，n 从 2 开始。

已提交前缀 C_epoch 必须与自由假设兼容；候选只从已提交位置之后增长。若 H_k 不以 C_epoch 为前缀，不能简单跳过相同字符数后继续追加。转入冲突状态，保留原始假设，暂停新增稳定提交并等待更多音频或触发明确更正。

尾部保留在草稿中，并切回合法 Unicode/词片边界。中文不按空格分词。时间戳从显示比较中去除，但数字、否定、单位、专名和真实重复不能被“标准化”删除。

**连续两次相同是经验稳定证据，不是语义正确性证明。** 训练未适配时，短前缀可能稳定地产生同一个错误。验证集必须检查这种错误。

### 8.4 保守模式与句中模式

保守模式优先提交完整且重复确认的 cue，源边界远离本次实际输入尾端；它可能只达到 L1。

句中模式允许在 cue 内确认目标短语，但没有可靠细粒度对齐时仍保留当前音频起点。源词结构不完整、开放数字、否定未闭合等风险特征可延后提交；规则只能作为启发式，不能当形式证明。

训练前不能保证所有英中句子都有低延迟可提交前缀。若 LCP 长期不增长，正确结论是该配置存在等待问题，应优化或训练，而不是靠提前锁定错误文字制造低延迟。

### 8.5 前缀强制续写

若强制模型重复已提交文本，两次输出相同不再是独立验证。目标前缀约束须单独记录模式；至少保留自由重译诊断，检测与已提交内容的矛盾。它用于维持一致性，不能单独证明正确性。

### 8.6 注意力门控

AlignAtt4LLM 可提供适配思路，但 Echo 使用音频嵌入并含混合注意力层。需要识别真实音频位置、可用完整注意力层、头与右边界关系，并在开发集标定。禁止复制别的模型的层号/头号，也不能将线性注意力状态当作标准注意力矩阵。

关注门控实现是否迫使关闭高效 attention kernel、引入每 token 设备同步，以及是否因此失去实际速度收益。该功能在 B2 基线完成后再进入。[S07, S21–S23]

## 9. 历史、切窗、重复与漏译

### 9.1 两类提交分离

目标文本可以被提交，不代表对应源音频已经被完全消费。英文和中文词序不同，目标字符数量不能映射为源音频时长。

固定 epoch 起点并保留当前语义段音频，直到存在可审计的源边界。边界来自已观测音频、已完成源区间与译文覆盖的组合，而不是模型预测时间戳单一证据。

### 9.2 时间戳使用限制

模型时间戳是预测，不是评测金标。不合法、超出快照、倒序或大幅漂移时标记低可信。不可静默裁剪到合法范围后继续作为“可靠对齐”。

切窗候选需要满足：边界属于本次 used_end 之前的已观测区间；该源区间的译文已处理；没有未闭合尾 cue；保留一定重叠；裁剪前后可通过源转写/时间区间检查覆盖。

### 9.3 去重

跨窗基于源区间身份、时间重叠和源文本匹配共同判断。仅因中文字符串重复就删除，会把讲话人真实重复的一句话丢掉。相反，没有源区间检查的字符串拼接也会造成重叠重复翻译。

跨 epoch 后重置 LCP 比较，不能将新旧两个不同音频起点的整段译文直接比较。

### 9.4 长时间无安全边界

设软边界和硬上限。优先在软边界之后寻找已观察到的安全位置。无法安全裁剪且接近硬上限时，进入可见降级：报告缓冲压力并选择已定义的强制分段实验或有界停止。

默认不静默丢音频、不无限增大缓冲、不把不完整语义强行标成正确最终译文。强制分段必须记录 `forced_boundary` 和未覆盖区间，质量单独统计。长流若因此不能连续工作，应报告未通过验收。

## 10. 缓存与原生流式的边界

### 10.1 三种不同缓存

模型常驻：必做，避免重复加载。

同一冻结快照的一次生成内部缓存：按模型支持使用。

跨新增音频更新的编码/解码状态：首版关闭，后续单独证明。

### 10.2 为什么跨更新不能直接复用

新增音频可能改变窗内特征归一化、编码器右上下文、音频 token 数、指令/目标文本位置。旧目标状态是在旧音频条件下产生的，不能直接视为新条件下正确。混合架构除 KV 外还可能有卷积/递归状态，必须一起处理。[S05, S07]

要审查实际前处理、卷积、块内/块间 mask、位置编码、缓存回滚能力及状态 dtype。无法证明不变的前缀就重新计算；正确但慢的基线不可删除。

### 10.3 原生流式研究顺序

先测编码占比；若是主要瓶颈，再研究块因果音频塔。重新定义块大小、右上下文、训练/蒸馏目标和精度回归。Qwen3-ASR-causal 使用专门微调的塔且披露语言/质量限制，不能直接移植权重，也不能继承其速度数字。[S24]

再研究新增音频条件下解码器的增量输入布局；音频与已生成目标 token 如何交错必须与训练和缓存规则一致，不能简单在已生成文本之后追加音频 embedding。

## 11. 调度、积压与多会话

### 11.1 首版调度

一个运行中任务，一个待执行最新快照。收到新音频只更新待执行快照，不排入无限个历史任务。合并的是推理请求，不是输入语音。每个结果必须匹配 session/epoch/history/generation 的有效状态，旧结果不得覆盖更新后的字幕。

结束消息到达时，必须安排覆盖最后一个已接收样本的 final 快照；不能因为先前任务正在执行就遗漏尾段。超时/取消不一定能立即中断设备 kernel，worker 退出和资源释放要有独立检查。

### 11.2 可持续性计算

更新间隔为 Δ，平均一轮成本为 C。单 worker 若每个更新都执行且 C>Δ，会积压。窗口长度 W 不能替代新增输入时长作为实时性分母。

假设每 1 秒重译最近 8 秒音频，一轮花 1.5 秒；1.5/8 看似小于 1，但每新增 1 秒需要 1.5 秒计算，实际不可持续。这只是推导例，不是 Echo 实测。

### 11.3 多路容量

并发 N 的粗略必要条件为 Σ(C_i/Δ_i)<1；它不是充分条件，还要考虑峰值、内存、排队公平性和最终尾段任务。初始准入可保留约 30% 调度余量，实际用压力测试校准。

单卡单会话通过后，依次测试 2、4、8 等并发等级，失败即停止扩容。单卡放得下多份权重不代表吞吐更好。先共享一份模型并串行调度，再研究受支持的批处理。不同音频长度 padding 必须正确掩码。

### 11.4 分布式取舍

首版一张卡一个模型 worker，多卡按会话分配副本，不做一个会话横跨 NVIDIA 与 Ascend。容量需求确立后再评估张量并行或多实例；不能将 NVLink/HCCL/NCCL 当作自动加速按钮。

## 12. NVIDIA A800/A100 部署方案

### 12.1 现场盘点

记录 nvidia-smi 的型号、显存、驱动、MIG 状态、设备 UUID、PCIe/NVLink 拓扑，以及 CPU 架构、NUMA、RAM、磁盘、其他任务。A800 不应默认都是 80 GB；官方也有 A800 40GB Active。此事实不代表用户机器一定是该 SKU。[S14]

首个性能基线使用空闲独占设备和明确的可用资源配额。若 MIG/共享卡不可避免，报告实例资源，不拿整卡名称代替实际容量。不要未经授权更改 MIG、驱动、功耗或系统配置。

### 12.2 参考环境

候选 Python 3.11；官方 Echo 声明的 PyTorch 2.11.0、Transformers 5.6.0 为起点。CUDA wheel、驱动和操作系统必须匹配并冻结。禁止让编码代理机械安装所有包的 latest。

优先 BF16 参考精度，Ampere Tensor Core 有 BF16 支持。敏感累积/状态按模型实现保持相应精度，不把所有浮点张量一律强制 BF16。FP16 是独立实验，需要检查 NaN/Inf 和质量差异。[S04, S13]

第一版不依赖 FP8/INT4。量化格式可用、权重能加载与硬件获得有效加速是三个不同问题，必须分别测量。

### 12.3 环境隔离

至少分 `runtime-nvidia`、`runtime-ascend`、`evaluation` 三套依赖锁/镜像。COMET 等评测依赖不进入在线推理环境，防止 Transformers/PyTorch 被依赖解析器改写。simulstream 自身也提示评测依赖可能冲突。[S01]

镜像用 digest 固定；模型、数据、日志外部挂载。记录 Python、Torch、CUDA runtime、驱动、Transformers、attention backend、编译器、模型 revision 和本地补丁 hash。

### 12.4 2B 与 9B 的内存规划

2B 用于工程主线；9B 用于质量对照。参数规模标签不是完整显存需求。

近似分解：

`峰值显存 = 权重 + 音频编码激活 + prefill/生成激活 + full-attention KV + 线性/卷积状态 + 工作区 + 分配器保留 + 并发开销`。

权重字节可按 `Σ 参数量 × 每参数存储字节` 估算；再以实际加载及最长窗口测量。9B 脚本沿用的通用“约 10GB”注释不能作为 9B 部署保证。[S05–S07]

规划时给实测峰值额外保留 20%–30% 余量；40GB 和 80GB 分别测试。先单独启动 2B/9B，避免两个模型与评分模型共卡污染结论。本文不预先保证任何卡上某个并发数或长窗口都能容纳。

### 12.5 性能优化顺序

去除重复加载和每轮磁盘 I/O → 收音/推理解耦 → 控制重复窗口与输出 token → 检查实际 attention/线性算子路径 → 少量形状预热 → 受控批处理/量化 → 经验证的推理引擎或缓存改造。

先用 eager/reference 路径保证可追踪。CUDA Graph、torch.compile、FlashAttention 或 Triton kernel 都是可关闭的实验，不默认所有音频塔/线性层都支持。形状分桶 padding 必须保持有效长度和 mask，不能为了静态图改变模型可见内容。

warmup 单独报告，不计入稳态但不能隐藏冷启动。profiling 使用设备事件或明确同步边界，不在每个 token 任意 synchronize 而改变调度。禁止每轮调用 empty_cache 作为常规优化。

## 13. 昇腾 910B 迁移方案

### 13.1 迁移原则

共同使用同一套权重、tokenizer、输入规范、提示、解析、策略、事件和评测数据；允许不同设备 provider、算子实现和独立依赖锁。首先追求功能/数值可解释，再追求速度。代码可迁移不等于已有原生 NPU 支持。

### 13.2 现场信息

npu-smi 识别实际板卡/芯片、可用 HBM、健康状态和拓扑；记录 x86_64/aarch64、驱动、固件、CANN toolkit/kernel 包、TorchNPU、Python 和 glibc。不要将 Ascend 910、910B、A2 产品线和具体服务器型号混作同一个精确 SKU。

### 13.3 版本候选与限制

本次官方 TorchNPU 矩阵列出的候选为 PyTorch 2.11.0 + TorchNPU 2.11.0.post2 + CANN 9.1.X。它与 Echo 声明的 Torch 主版本有交集，但仍须确认实际 910B 的驱动/固件/OS 支持以及 Transformers 所需算子。[S08–S09]

不能因该候选存在，就直接升级服务器系统。先检查现场已部署组合；必要时在独立受支持镜像做验证。无法形成受支持组合时，记录阻塞原因，在验证分支处理兼容，不修改原 CUDA 环境。

### 13.4 算子逐层验收

| 模块 | 验收内容 | 首版处理 |
|---|---|---|
| 音频读取/重采样/mel | 分块状态、dtype、有效帧和归一化一致性。 | 尽量保留共同 CPU 路径，避免先迁移 STFT 复杂算子。 |
| 音频编码器 | 卷积、attention、mask、长度张量、位置编码、动态形状。 | 先标准实现，再专用 kernel。 |
| 连接模块 | 两种连接结构、GELU/线性投影、权重键。 | 保持数学语义和严格加载。 |
| embedding 注入 | bool mask、索引写入、设备一致性、音频 token 数。 | 单独小规模测试，不能仅测试文本提示。 |
| 完整注意力层 | 旋转位置、归一化、attention 与 KV。 | 核查 NPU 支持和 fallback。 |
| 线性/门控层 | 递归状态、卷积、累积精度、非 CUDA 路径。 | 重点审查 CUDA/Triton 依赖及 PyTorch 参考分支。 |
| 自回归生成 | EOS、position/cache、greedy/beam、动态 token 长度。 | 先单样本固定快照。 |
| 服务行为 | 同步、取消、内存峰值、并发隔离、日志时钟。 | 与 CUDA 同一事件测试。 |

CUDA 专用 `.cuda()`、CUDA event、流、fused extension、bitsandbytes 或 Triton 路径需要逐项盘点。优先封装/替代，不全项目文本替换成 `.npu()`。对 CPU fallback 做设备追踪；能够输出结果但主要计算偷偷回 CPU，不算 NPU 性能验收通过。

### 13.5 DeviceProvider 合同

提供设备选择、能力探针、张量搬运、autocast 上下文、同步、计时、内存统计和异常转换；具体方法以本地库可用 API 实现。CPU 核心测试中不得导入 torch_npu/CUDA 专用扩展。

不要把平台 SDK 对象序列化进公共会话状态。多进程使用安全启动方式，模型只在目标 worker 初始化，不在父进程设备上下文创建后随意 fork。

### 13.6 数值一致性顺序

先 CPU 预处理一致 → 音频塔输出 → 连接输出 → 固定 prompt 的一次 forward/logits → 固定目标 token 的 teacher-forced 轨迹 → 自由生成 → B0/B1/B2 流式任务。

逐层保存误差分布、NaN/Inf、top-k/logit 差异。跨硬件低精度不要求逐 bit 相同；自由生成分叉也不能自动认定是算子错误。利用固定输入、固定目标序列和首次差异定位，再结合任务质量判断。数值阈值须按层类型/精度和开发集确定，不统一用一个宽松阈值掩盖错误。

### 13.7 vLLM-Ascend 与 MindIE 的位置

vLLM-Ascend 的 Qwen3.5-Dense 教程是相关架构参考；其文本/视觉模型支持不证明 Echo 音频塔 + connector + inputs_embeds + 混合状态完整可用。所查支持模型页未出现 Index 名称，不能声称官方整包已适配。[S10–S12]

所查 vLLM-Ascend README 采用的 PyTorch 2.10.0 / TorchNPU 2.10.0.post4 与 Echo 声明的 Torch 2.11.0 不同；这是独立环境和回归的具体理由，不应混装后交给包管理器自行降级。[S10]

只有在 TorchNPU 参考路径跑通、profiling 指明收益后，再做引擎适配。新增 engine adapter 须与 HF 参考进行 prompt、embedding、位置、停止规则与质量对照。MindIE 同样按具体版本/模型支持合同评估，本方案没有验证其 Echo 支持，不作兼容承诺。

### 13.8 迁移完成标准

同一批真实音频、相同提示/策略下，910B 通过组件、方向、长流、状态隔离和质量回归。报告独立延迟/显存/并发，不以 A800 结果代替。若精度通过但速度未达标，结论为“功能适配完成，性能未通过”；若仅文本解码器能跑，结论为“Echo 整包尚未通过”。

| 参数 | 初始候选 | 约束 |

| 一致性轮数 | 2 | 与 3 对照；必须新增音频。 |
| 尾部保留 | 先保留最后未闭合短语 | 字符数阈值只是备用启发式。 |
| 源尾保护 | 0.3/0.6/1.0s 候选 | 对照 used_end，不是更新后的 received_end。 |
| 软/硬缓冲 | 12s / 30s 候选 | 无安全边界不能静默截断。 |
| 已确认上下文 | 少量完整双语段 | 另设 token 上限；epoch 内固定。 |
| 精度 | NVIDIA BF16 起点 | Ascend 逐算子确认；FP16 单独回归。 |
| 并发 | 1 | 单卡验收后按档位扩大。 |
| 缓存 | 常驻 + 单次生成内部 | 跨更新状态复用首版关闭。 |

配置分 audio、model、device、policy、transport、scheduler、logging、evaluation。生产配置启动前做 schema 校验；未知键拒绝，不默默忽略。所有配置与实际运行 hash 写入结果。

## 15. 评测、验收与数据

### 15.1 两类回放

因果模拟用于算法比较，严格按前缀投递；可明确选择忽略计算时间以估计策略下界，但必须标记 computation-unaware。

真实时钟回放按 1× 速度发送，网络接收与推理并行，记录计算和排队。真实麦克风再验证端到端链路。不能把第一类数据宣传为实际部署延迟。[S18–S19]

### 15.2 最小日志

环境/模型/提示/策略版本；音频来源与权限；session/epoch/event；接收/使用/裁剪采样点；排队和开始/结束时刻；raw hypothesis；解析状态；草稿快照；提交/更正；token 数和结束原因；队列长度/音频年龄；设备内存；客户端接收/展示时刻。

跨机器不能直接相减未校准的单调时钟。单机回放优先同一基准；跨机明确校时或用可解释的往返/客户端观测方法。

### 15.3 指标体系

质量：最终译文 chrF、明确中文分词设置的 BLEU；需要时离线 COMET，记录权重/版本。源转写与目标翻译错误分开。人工评估数字、极性、否定、单位、专名、重复/漏译。

增量质量：实际已提交序列与更正的轨迹，不拿最后一次完整离线精修替代在线历史。

延迟：首条草稿、首条有意义提交、持续语义延迟 p50/p95、句中正确提交比例。小集标注目标语义所需源信息的最早结束时刻，避免用句首/模型预测时间戳偷换口径。长流指标采用锁定实现的 StreamLAAL 等，并明确计算感知与修订处理。[S19–S20]

稳定性：草稿擦除量、修改次数、已提交冲突/更正率。文本不可修改的实现不等于文本正确。

计算：编码、prefill、生成、解析、排队、网络/展示分解；总耗时除新增唯一音频时长；内存峰值、长流内存斜率、积压趋势和多路公平性。

### 15.4 数据计划

最小健康集：官方方向若干样例；英中 100 条人工核查短片段，开发/保留按来源或说话人隔离。为每条建立多个严格截断前缀，不能把同一句的不同前缀分散到开发和保留集合。

专项集：否定最小对、日期/数字/单位、专名、口音噪声、断词、长从句、修正重复、无停顿、静音、真实丢包、混说。参考翻译接受合理同传重排，避免只有一个离线字面译文造成误判。

长流：开发至少 1×30 分钟；验收建议不同来源 3×30 分钟，并做更长 soak。具体数量是设计，不表示已取得数据。音频必须有使用权限，麦克风默认不落盘。

### 15.5 建议门槛

因果性：零未来样本访问；源区间覆盖和缺口全部可追溯。

可靠性：无会话串线、静默提交回滚、无解释音频丢失；30 分钟运行无持续发散积压；错误有明确返回。

质量：先以同模型 B0 为参照，开发目标可设最终 chrF 降幅不超过约 2 分（0–100 口径），并要求关键否定/数字回归无新增错误。它是候选门槛，须结合具体场景冻结，不代表本模型必达。

延迟：稳定语义延迟 p50 约 2–3s、p95 约 5s 可作研发候选；必须使用已定义语义时刻并计入真实计算。达不到如实报告，不更改口径。

双硬件：各自通过相同正确性集合；各自报告性能目标通过/失败，不能声称数值不完全相同就是迁移失败，也不能用最终几句相似掩盖大量偏差。

## 16. 实验矩阵与决策逻辑

按阶段，而不是一次遍历全组合：

E0 官方加载健康 → E1 完整英中 2B/9B → E2 前缀轨迹 → E3 B1/B2 提交比较 → E4 上下文/尾部/步长单变量 → E5 A800/A100 真时钟/长流 → E6 并发和资源 → E7 910B 组件/自由生成 → E8 双平台 B0/B1/B2 → E9 有证据的优化。

完整英中差：先查路由、组件和解析，再讨论模型或训练，不能靠流式框架修复。

完整英中好而前缀差：考虑 prefix-to-prefix 数据、等待决策与增量译法。

前缀好而运行跟不上：优化重算、输出预算、算子与引擎。

模型好而漏译/重复：修复源区间、切窗与提交合同。

NPU 组件差异大：先修数值和算子，不开展门控/量化优化。

## 17. 后续训练与原生流式路线

用户前面考虑的 DIRECT/FLEX 文本单元可以作为数据构造的输入，但 S2TT 训练还需要音频位置、可见源前缀、已提交历史和应等待的情况。不能把依赖后文的完整译文前半段直接当作当前音频前缀标签。

数据样本建议包含 audio_id、visible_end_sample、source_prefix、committed_target、next_target_unit、evidence_end_sample、action/read_write、上下文和标注依据。教师可用全文辅助整理，但可提交目标必须经可见前缀证据检验；在线模型输入不得包含未来信息。

先做提示/解析和等待策略消融，再考虑解码器 LoRA/SFT；是否训练 connector/音频塔由错误分解决定。音频塔因果化、跨块位置与状态复用需要单独训练和一致性试验。

模型、训练数据、提示格式和在线解码必须同步版本。NVIDIA 训练出的普通权重是否在 NPU 推理保持质量，也要重新验收；不要把训练框架迁移与推理迁移同时作为第一阶段任务。

## 18. 安全、运维与生产边界

本地演示默认只监听受控接口，通过受控网络/隧道访问；对外服务需要 TLS、鉴权、源限制、会话/消息大小/速率限制与超时。不直接公开无鉴权模型接口。

模型路径、可加载版本和配置白名单；禁止客户端触发任意模型下载、shell 命令或文件读取。依赖和模型来源固定、校验 hash，不自动执行未知远程代码。

日志默认记录元数据和必要事件，原始音频/文本调试需显式开启与保留期限；训练和评分样例脱敏。不要把用户音频发送到未授权外部 API。

提供 liveness/readiness 区分：进程活着不代表模型可接单；预热失败或设备故障不能继续报 ready。优雅退出停止准入、排空或明确失败会话；不得重启后伪装未中断。

模型 OOM、设备异常、解析失败、积压超限、状态冲突分别编码。升级采用 canary/回滚并冻结旧版基线；不能热改模型/提示而不重置会话状态。

生产多租户、持久化恢复、权限审计和高可用是功能基线后的独立门槛，不由 simulstream 自动保证。

## 21. 顶层风险清单

R1 英中方向/前缀能力未通过；R2 2B/9B connector 或字段误配；R3 全文件预处理泄漏未来；R4 模型尾部补全幻觉；R5 错误的前缀去重；R6 按文本长度剪音频；R7 跨更新缓存错误；R8 在线积压被窗口 RTF 掩盖；R9 设备专用 kernel 阻碍 910B；R10 dtype/递归状态数值退化；R11 评测依赖污染运行环境；R12 真实麦克风/断连/尾段没有测试；R13 过度并发 OOM；R14 在线错译被最后离线修订掩盖；R15 mock/CPU fallback 冒充模型/NPU 成功。

每项风险都应在任务书与测试目录有对应检查，不能仅在会议上口头提醒。

## 22. 最终实施决策

先在 A800/A100 完成真实、可追溯的系统级流式同传；同时以设备隔离和版本管理为 910B 预留迁移边界。真正优先级为：**方向与原模型正确 → 因果输入 → 提交与切窗正确 → 可持续运行 → 延迟/质量平衡 → 跨硬件正确 → 专项加速。**

下一项本地任务不是大型前端或通用 gRPC 封装，而是 M0/M1：冻结环境与模型，完成 2B/9B 的真实英中和音频前缀探针，并保留全部原始证据。
